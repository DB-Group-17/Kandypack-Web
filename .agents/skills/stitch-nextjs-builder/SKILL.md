# Stitch → Next.js Builder

## What this does

You have a batch of page mockups generated by an AI UI tool (e.g. Stitch) — one folder per page, each containing a screenshot and an HTML file. Individually these pages are rarely consistent with each other (different button radii, different heading sizes, different spacing) because each was generated independently. This skill turns that folder of loose pages into one coherent Next.js app by extracting a shared design system *first*, then building each page against it — flagging anything the design system doesn't cover instead of guessing.

Two commands:
- **`ui init`** — reads every page folder once and produces two project-level documents: `design.md` (the visual theme) and `ui-rules.md` (component and layout rules).
- **`ui build <page>`** — builds one page in Next.js using those two documents as the source of truth, the page's own image/HTML as the structural reference, and a separate content copy as the actual text.

Run `ui init` before the first `ui build`. Re-run `ui init` only if the input pages themselves change — `ui build` reads the existing docs and updates them incrementally as new decisions come up, so it doesn't need a fresh `ui init` between pages.

## Expected input layout

```
<pages-root>/
  home/
    home.png  (or .jpg/.webp — one image)
    home.html
  about/
    about.png
    about.html
  pricing/
    pricing.png
    pricing.html
```

Each folder name is the page name. If a folder is missing either the image or the HTML file, skip it and tell the user rather than guessing — both matter (HTML for the actual markup/classes, the image for how it actually renders, since generated HTML doesn't always render the way it reads).

Content copy — the real, client-approved text, as opposed to the mockup's placeholder text — lives separately from the mockups. Look for it in this order:
1. A `content.md` or `copy.md` file inside the page's own folder.
2. A top-level `content/<page-name>.md` next to the pages root.
3. If neither exists, ask the user where the content copy for that page lives before building. Never invent copy or ship the mockup's placeholder text into the build — that defeats the point of keeping the two separate.

## Command: `ui init`

**Goal:** one `design.md` and one `ui-rules.md` for the whole project, not per page. The point of this step is to stop the pages from having six different button styles, so the outputs must be singular and consolidated.

1. Go through the page folders one at a time. For each, read the HTML (actual class names, inline styles, structure) and view the image (how it actually renders — rounding, shadows, and spacing are easy to miss in raw markup but obvious in the screenshot).
2. Extract, per page:
   - **Colors** — hex/rgb values in use, and what role each plays (primary action, background, text, border, success/error states).
   - **Typography** — font families, and the size/weight/line-height used for each heading level, body text, and captions.
   - **Spacing** — the padding/margin/gap values in use, so you can infer the base unit (4px, 8px, etc.) and the scale built on it.
   - **Component shapes** — border-radius, shadow, and border treatment on buttons, cards, inputs, and any other repeated element.
   - **Layout patterns** — container max-widths, grid vs. flex usage, section spacing, breakpoints if visible.
3. Once every folder has been read, consolidate into the two documents below. Where pages agree, that's a rule. Where pages *disagree* (one page uses an 8px button radius, another uses 4px), don't average or silently pick one — list it as an open conflict at the bottom of the relevant doc and ask the user which is canonical. Making that call once, at init time, is what stops the same argument from repeating during every later build.

## Command: `ui build <page>`

**Goal:** build `<page>` in Next.js so it matches the reference image/HTML structurally, uses the real content copy rather than mockup placeholder text, and pulls every visual value from `design.md`/`ui-rules.md` rather than re-deciding it from the mockup.

Before starting, confirm `design.md` and `ui-rules.md` exist at the pages root. If not, run `ui init` first (or tell the user to).

1. **Read the references.** Open the page's HTML and image, plus `design.md`/`ui-rules.md`, and locate its content copy per the lookup order above.
2. **Reuse before creating.** Check `/components` for an existing Button, Card, Navbar, etc. before writing a new one — the whole value of doing this in Next.js instead of raw HTML is that a Button built once, from `ui-rules.md`, gets reused everywhere, so it can't drift between pages. Only add a new component if this page genuinely introduces one that doesn't exist yet, and add it to `ui-rules.md` when you do.
3. **Wire the theme once.** Encode `design.md`'s colors, typography, spacing, and radii as Tailwind theme tokens (or CSS variables) instead of hardcoding hex/px values inside individual components — that way a later change to the design doc updates every page instead of requiring a find-and-replace across the codebase.
4. **Build the page.** Match the layout, section order, and component structure from the image/HTML. Swap in the real content copy for every piece of text — headings, body copy, button labels, alt text — in place of the mockup's placeholder text.
5. **When something isn't covered:** if the page needs a visual decision that isn't in `design.md` or `ui-rules.md` (a new color, an unlisted spacing value, a component shape not seen before), stop and ask the user instead of picking something that looks plausible — a guessed value here is exactly the kind of silent inconsistency this whole process exists to avoid. Be specific about the choice, e.g.: "This page's hero card uses a 24px radius, but the design system only defines 8/12/16px — add 24px as a new option, or use the closest existing one (16px)?" Once the user answers, write the decision into `design.md` or `ui-rules.md` (whichever it belongs in) and add a row to the Decision Log in `ui-rules.md`, so the next `ui build` already knows the answer.
6. **Verify before finishing**, in two passes:
   - **Content pass** — go through the content copy piece by piece and confirm every heading, paragraph, label, and CTA made it into the built page as given (not paraphrased or dropped), and that nothing appears on the page that isn't in the copy.
   - **Visual pass** — compare the built page against the reference image and HTML: same sections in the same order, same component types in the same places, same general proportions. A value that differs *because* it now uses the canonical design-doc value instead of this page's one-off is correct, not a bug — flag anything else that doesn't match.
7. **Report back.** Briefly summarize what was built, anything you had to ask the user about, and anything that got added to `design.md`/`ui-rules.md` as a result.

## Notes

- **Build order matters.** Build the page with the most UI variety first (usually the homepage) — it tends to establish most of the shared components, so later pages go faster and raise fewer open questions.
- **Don't let `ui build` re-open settled design decisions.** If `design.md` already defines the primary button, use it as-is even if this particular mockup drew it slightly differently — the mockup is a structural reference, not the source of truth for values already captured in the design docs.
- **Keep the Decision Log growing, not the docs sprawling.** When a decision is confirmed, fold it directly into the relevant section of `design.md`/`ui-rules.md` (e.g. add the new radius to the scale). The Decision Log row is just a dated pointer to when and why — not a duplicate of the rule itself.
